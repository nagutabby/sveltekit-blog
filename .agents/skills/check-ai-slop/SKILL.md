# AI slopのように見えるか点検する

完成済みの成果物を読み、読者に「AIが書いたような文章」と感じさせる箇所と、内容上の問題を特定する。制作手段や使用したモデルの鑑定ではなく、文体と内容についての編集上の評価を行う。`new-article` などを経由せず、`$check-ai-slop backend/content/articles/2025-08-14.md` のように直接呼び出せる。

## 対象の受け取り方

- 呼び出し時にファイルパス、記事・書評のID、スライド名、または本文が渡されたら、それを対象にする。記事は `backend/content/articles/`、書評は `backend/content/reviews/`、スライドは `web/static/content/slides/` を探す。貼り付けられた本文もそのまま点検できる。
- 対象の指定がなくても会話の直近で扱った成果物が一つに定まるなら、それを使う。候補が複数ある、または対象を特定できない場合だけ、パス・ID・本文のいずれかを尋ねる。リポジトリ全体を無差別に採点しない。
- Markdownのfrontmatterは題名や説明文の文脈として読むが、判定の中心は本文に置く。本文が空なら判定材料不足と伝える。スライドはHTMLまたはPDFの内容を読み、図表も確認できる範囲で点検する。

## 手順

1. 対象全体を読み、形式、想定読者、中心の主張、書き手の立場を把握する。記事・書評は本文まで、スライドは各ページの文面とページ間の流れを見る。表示結果があれば図表も確認する。
2. 内容を点検する。主張に対する根拠と論理、題材固有の情報、重要な留保があるかを見る。事実・数値・引用・書誌情報は、判定に影響するものから確認可能な一次資料と照合する。調べていない箇所は「未確認」、資料が足りない箇所は「根拠不足」と区別し、誤りと決めつけない。
3. [文体の実例と点検項目](references/signals.md) の共通項目と該当形式の項目を確認する。表現の出現そのものではなく、反復、文脈との不一致、情報の欠落を根拠にする。
4. 同じ書き手の既存コンテンツが読める場合は語り口、文末、具体例の選び方を比較する。以前と異なるだけでは問題にしない。今回の題材や読者に合っているかを見る。
5. **「AI slopの印象が強い」「一部にAIらしい癖がある」「目立たない」「判定材料が不足」** のいずれかを結論にする。文体上の癖と、内容・根拠の問題を分けて説明する。
6. 問題箇所を短く引用またはページ・段落で示し、読者がどう受け取るかと最小限の改善案を述べる。判定依頼だけならファイルを編集しない。本人の経験、読書感想、実測値、出典を創作しない。

定型句一つや整った構成だけでAI生成と断定しない。短文や未完成の成果物は判定を保留できる。AI生成確率の数値は出さない。
